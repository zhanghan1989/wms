# 系统看板优化（2026-10-07）

本轮修改保存在本地，尚未部署；未修改生产数据库或执行数据库迁移。

## 已实施

- 基础库存合计在 MySQL 中求和，不再下载全量产品再累计。预占、在途、已安排生产仍保留原有启用产品、肩带配件排除和历史 SKU 唯一映射规则。
- 完整看板先读取统计来源，只读取相关 SKU，以及非零库存、订单、FBA 库存快照、预占、在途、已安排生产或组合商品引用的产品。零库存但有销量的产品仍参与统计；正库存无销量和负库存产品仍保留。
- SKU 查询保留主 SKU、FBM、乐天别名的全部匹配，不提前选取单一匹配，因此重复关联、渠道冲突和店铺匹配仍由原逻辑判断。代码在 SQL 中使用 TRIM 匹配历史空格数据，参数化查询每批最多 500 个代码；产品查询每批最多 500 个编号。
- 启用产品总数独立使用数据库 count，保持总数口径，不以实际加载的相关产品数量替代。
- 看板不同参数的计算共用串行队列；相同参数合并请求。后台旧数据刷新和强制刷新保留原缓存行为。工厂备货建议导出也使用同一计算入口，强制获取新结果，避免绕过队列。
- 批量库存更新后，非当前页面的看板只失效缓存，下一次打开才请求更新。当前正在展示的看板立即刷新。旧请求通过版本和登录会话检查，不能覆盖库存变更后的新结果。

## 验证

类型检查、构建、前端 JavaScript 语法和差异格式检查通过。完整测试：40 个套件、398 项通过；29 项数据库集成测试因缺少测试数据库跳过。

新增或调整的回归验证覆盖：正负库存、零库存但被引用的产品、无关和停用产品排除、分批查询、重复别名、不同店铺同 SKU、渠道冲突、库存合计、组合商品拆分、FBA 备货建议、产品总数、并发排队及失败恢复、隐藏看板延后刷新、旧响应丢弃和备货表导出。

## 合成目录对比

本地使用 272,408 个产品及同等数量 SKU 的合成目录，其中 600 个产品有库存，400 个 SKU 被统计来源引用。数据库出口用按查询条件生成记录的模拟实现；两种路径均构造产品、SKU 别名、主 SKU、店铺及渠道映射，并在强制 GC 后读取存活堆增量。

| 路径 | 加载产品数 | 加载 SKU 数 | 总库存 | 存活堆增量 |
| --- | ---: | ---: | ---: | ---: |
| 全量目录 | 272,408 | 272,408 | 6,000 | 501.0 MiB |
| 相关目录 | 600 | 400 | 6,000 | 0.8 MiB |

这些数字只用于展示目录读取与索引构造的规模差异，不包含 MySQL、订单读取、看板全部计算、RSS 或线上网络耗时；不能作为线上内存或响应时间承诺。相关产品数量取决于实际库存与销量分布。

## 上线后确认

部署 API 与前端后，对照 30/60/90 天统计、零库存销量、无销量库存、库存健康和工厂备货导出；记录首次加载、强制刷新和多用户切换周期时的请求耗时、进程内存和数据库查询耗时。

本轮没有引入持久化日销量汇总或定时预计算，也没有添加 SKU 标准化索引。TRIM 查询仍可能扫描 SKU 表，原始 90 天订单仍按现有方式读取；如果这两部分成为下一阶段瓶颈，再依据数据库执行计划和实际订单规模优化。

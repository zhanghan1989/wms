# 2026-10-28 磁盘写入与容量优化

调查依据见 [云盘增长调查](archive/history/云盘使用率增长调查_20261028.md)。此次优化减少新增写入，并提供可预演、带恢复前置条件的存量日志维护工具。

## 应用变更

- 新表 `rakuten_tracking_checks` 按运单保存实际查询时间、下次查询时间和连续失败次数。物流业务字段仍在订单表，保证回传、清关和邮件读取已有事实。
- 首次查询或物流事实变化时，才按运单更新订单行；重复相同状态只写轻量表。两者在同一事务提交，元数据写入失败会回滚业务字段更新。
- 普通在途运单仍按 20 分钟周期查询。连续错误按 20、40、80…分钟退避，最长一天；已送达但清关信息缺失的运单每日补查，完整终态停止查询。恢复被忽略的运单时清除退避，可参与下一轮查询。
- 到期与忽略过滤在 SQL 的 LIMIT 之前执行，避免错误运单占满候选窗口。轮询只读取物流字段，不读取订单 JSON；新增运单组合索引。
- 订单列表和失败列表从轻量表补充最新查询时间，保留历史值回退；换单后不会显示早于新单号登记时间的旧查询时间。
- RMS 同步跳过仅轮询时间变化的订单，JSON 比较忽略对象键顺序但保留数组顺序。真实业务或原始载荷变化仍按差异写入并保留回滚快照；冻结订单和同一人工观察结果不再反复更新时间。
- 备份文件检查跳过文件大小与可用标记完全一致的已有记录，避免每 15 分钟重复写入。

## 发布与回滚

先执行迁移 `20261028000000_rakuten_tracking_checks`，再部署应用。迁移仅增加轻量表和运单索引，不删除数据、不回填整张订单表。首次查询会逐步创建观察记录。

回滚应用可保留新表和索引：旧代码继续使用订单表已有物流事实。因新代码不把每次检查时间同步回宽表，回滚后旧页面显示的检查时间可能较旧，但业务状态仍保持一致；恢复旧代码也会重新产生原来的重复日志。

## 部署容量保护

`wms-disk-check.sh` 预留默认 2GiB 可用空间；镜像上传前另预留压缩包大小四倍的临时工作空间。导入及迁移前再检查磁盘、内存和 PSI。无法读取磁盘或阈值异常时停止部署。

可用环境变量：`WMS_DEPLOY_MIN_DISK_BYTES`、`WMS_DEPLOY_DISK_PATH`。前者只能提高/调整明确的字节数，不能用关闭检查绕过容量故障。

## 容量监测

部署成功后安装 `wms-storage-health.timer`，每小时记录使用率、剩余字节、空间增长速度、预计可用天数和 binlog 总量。状态位于 `/var/lib/wms-storage-health`，日志可通过以下命令检查：

```bash
systemctl status wms-storage-health.timer
journalctl -u wms-storage-health.service -n 30 --no-pager
cat /var/lib/wms-storage-health/latest
```

默认 75% WARNING、85% HIGH、90% CRITICAL；低于 5GiB 或按增长速度估算不足七天也告警。非 OK 状态使检查返回非零，严重程度变化时写入 syslog；不主动发送邮件或即时通讯消息。增长率使用至少一小时的基线，部署和清理会影响短期估算，需要与日趋势一起判断。

阿里云控制台告警或其他通知通道须另行接入现有运维接收人，本次工具不会创建未授权的外发消息。

## 二进制日志维护

工具默认只读预演：

```bash
python3 scripts/wms-binlog-maintenance.py --retain-days 7
```

它核对 `SHOW BINARY LOGS`、实际文件大小和关闭时间，计算可清理的连续旧文件前缀，始终保留当前活跃日志。前缀遇到新文件或大小不一致就停止扩展；不会直接删除 MySQL 文件。

执行清理之前，必须先验证可用备份的实际恢复，并核对离线复制、CDC 和恢复窗口。恢复验证凭据是本机 JSON 文件，权限应为 600，内容例如：

```json
{
  "backup_location": "实际备份的位置或标识",
  "restore_test_passed": true,
  "verified_at_utc": "实际验证完成的 UTC 时间"
}
```

该凭据是人工恢复验证的审计记录，脚本不会把“文件存在”当作真正做过恢复演练；也不会自动创建或上传备份。须记录独立备份位置及可恢复点，不能用同系统盘上的副本代替独立备份。验证时间必须在过去 24 小时内。

核对预演输出的 `purge_before`，再用同一个明确边界执行，示例中的名称必须替换为刚刚预演得到的值：

```bash
python3 scripts/wms-binlog-maintenance.py --retain-days 7 --apply \
  --expected-purge-before binlog.实际边界 \
  --verified-recovery-evidence /root/实际恢复验证凭据.json \
  --confirm-no-offline-consumers
```

执行阶段重新读取当前状态；如果边界变化、存在活跃复制客户端或上游复制通道，立即停止。确认后先用 MySQL `PURGE BINARY LOGS TO` 清理，再持久化七天保留期。审计记录保存在 `/var/lib/wms-storage-health/maintenance`。SQL 失败可能造成部分完成，必须检查审计与当前日志，不能盲目重跑。

`deploy/mysql/storage.cnf.example` 同时提供 `MINIMAL` 行镜像候选配置，默认不加载。只有核实恢复/CDC 兼容后才启用；全局调整不会改变既有会话，应用连接池需要受控重连并验证实际会话值。应用减写本身可在 FULL 模式下生效。

## 验证

- `npm run check:storage`：磁盘预留、异常读数、告警状态转换、容量预测、binlog 边界安全测试。
- `npm run lint`、`npm run build`、`npm run test`：类型、构建及全量回归。
- `node scripts/verify-storage-optimization.cjs`：仅允许本地 MySQL，创建并最终删除独立测试库；验证迁移零漂移、重复状态不修改宽表、UI 新鲜度、真实状态变更、事务回滚、候选过滤、错误退避和 RMS 载荷变化。需先构建，默认读取本地开发数据库连接但不操作该开发库。
- 上线后比较至少一个完整订单处理周期及一个完整业务日的 binlog 新增量和订单 UPDATE 增量；不能用未实施的清理预计值代替实际释放量。

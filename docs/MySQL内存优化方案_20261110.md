# MySQL 内存优化方案（待执行）

状态：仅完成只读调查和本地草案。尚未执行本文配置 SQL，未重启或更改线上 MySQL。本文与 SQL 草案均不接入自动部署、Prisma migration 或定时任务。

## 建议与预期

建议在一次低峰维护中保留 Performance Schema，缩小统计历史与摘要容量，按当前负载收紧缓存及连接上限。数据缓冲池保持 128 MiB。预计配置本身在同等负载下节省 **80–150 MiB**；这是估算，尚未做同版本隔离重启验证。

安排 **10–15 分钟维护窗口**，正常情况下业务不可用约 **1–3 分钟**，首次实施按 **3–5 分钟不可用**准备。若需回滚，额外预留 **2–5 分钟**。这是单机停库维护，不能承诺零停机；服务器操作系统无需重启。长事务、后台任务、磁盘延迟或恢复过程可能延长时间，应在执行前重估。

重启还可能释放历史分配留存，使 MySQL 的 RSS 与 Swap 合计短期再下降数百 MiB；这部分不计入稳定收益，也不保证不会增长。重启会把活跃页面重新放回 RAM，因此 **Swap 下降而 RSS 上升也可能正常**，不能只以 Docker 内存数字或 Swap 百分比判断效果。

| table_definition_cache | 2000 → 512 | 当前业务仅 78 张表，保留系统表及增长空间；不从这个上限差额直接换算节省量 |
| performance_schema_digests_size | 10000 → 3000 | 当前摘要 1307 条；保持约 2.3 倍空间，超过容量后会丢失部分诊断摘要，不影响业务数据 |
| performance_schema_events_statements_history_long_size | 10000 → 1000 | 缩短详细 SQL 历史，保留当前事件和汇总统计 |

保留 Performance Schema 开启、128 MiB InnoDB 缓冲池、现有单临时表 16 MiB 限额、事务持久性、binlog、认证及 SQL 模式。暂不限制 Docker 硬内存额度，避免在未知业务峰值时触发容器 OOM。

## 节省量如何估算

以同一查询负载下的已分配容量粗估，不把各项最大上限当作实际内存：

| 来源 | 计算依据 | 估算节省 |
| --- | --- | --- |
| SQL 摘要与 digest_text | (40.28 + 9.77) × (1 − 3000/10000) | 约 35 MiB |
| SQL 长历史、sql_text、digest_text | (14.42 + 9.77 + 9.77) × (1 − 1000/10000) | 约 31 MiB |
| 事务长历史 | 3.28 × 90% | 约 3 MiB |
| 其他统计、缓存和自动容量缩小 | 受实际实例数、分配粒度、并发及访问路径影响 | 暂估 10–80 MiB |
| 合计（取整） | 可量化约 69 MiB，加上述不确定部分 | **80–150 MiB** |

前三项按容量线性缩放，实际分配存在块粒度和按需增长，仍不是保证值。临时表 RAM 上限降低仅属于峰值保护，不纳入当前节省。若只看 RSS，不一定立即下降；应比较相似业务时段的 RSS + VmSwap、MySQL 内存分类与响应延迟。

不推荐直接关闭 Performance Schema：当前总计 249.4 MiB 并不是必然可节省的净值，关闭还会失去连接、锁和内存诊断能力；现有运维脚本也读取它。第一阶段不引入 malloc 替换或分配器环境变量，避免同时改变过多因素。

## 维护顺序与时间预算

| 阶段 | 操作 | 估时 |
| --- | --- | --- |
| 窗口前 | 备份验证、同版本离线验证、材料和镜像准备 | 单独安排，不占停机估算 |
| 收敛请求 | 维护提示，停止接收新业务；等待在途请求和后台任务结束，再优雅停止 API | 10–60 秒，任务未结束则延后维护 |
| 写入待启动配置 | 再次确认原配置副本后运行 SQL 草案；逐项核对 persisted_variables，发现部分失败则恢复配置、不重启 | 通常数秒 |
| MySQL 优雅重启 | 只重启现有 wms_db，不拉镜像、不运行全栈 compose up；停库允许至少 120 秒优雅退出，超时先诊断，不强杀 | 通常 15–60 秒，非保证值 |
| 验证并恢复入口 | 检查 SELECT 1、全部配置值、日志；启动 API；验证登录及公司范围、产品/订单列表，并检查任务能恢复后开放入口 | 20–60 秒 |
| 后续观察 | 按相近负载观测 30–60 分钟，再于 24 小时比较内存和业务性能 | 通常不需停机 |

单机 MySQL 停止时，数据库相关操作不可用；单纯首页 200 或未登录接口 401 不能替代业务验证。已有 API 在启动后通常可重连，但本次计划明确在窗口内暂停并恢复 API，避免请求撞上停库。

## 验收与回滚

验收必须核实 Performance Schema 仍为 ON、缓冲池仍为 128 MiB、十个目标参数生效；核对公司/产品/订单读取及公司权限，观察写操作的真实成功情况。内存对比同时记录 RSS 与 VmSwap，不要求原有 Swap 清零。保留新增 1 GiB 备用 Swap 和 swappiness=10。

若 MySQL 无法启动、出现无法解释的错误，或代表性业务接口延迟持续显著恶化（相同测试下超过基线约 20% 持续 10 分钟）、连接拒绝增加或内存压力加剧，按原配置回滚。缓存 Miss、临时文件 IO、Performance_schema_digest_lost 的增长用于定位具体取舍，不能仅凭重启后一次冷缓存请求判失败。

回滚顺序：保持维护入口和 API 暂停；优雅停止新配置下的数据库；使用相同镜像且不启动 mysqld 的工具容器访问同一数据卷，恢复维护前备份的 `mysqld-auto.cnf`。若维护前原文件不存在，仅删除本次生成的该文件。禁止删除整个数据目录、禁止覆盖数据文件、禁止使用 `down -v`。随后以原镜像启动原数据库，验证原参数、恢复 API 与业务入口。配置变更不涉及数据结构或业务行，不需要为配置回滚而恢复整库。

若数据库仍可启动，也可以用保存的原始 persisted_variables 逐项恢复；原本未持久化的目标参数使用 `RESET PERSIST IF EXISTS 参数名` 撤回，再安排必要的重启。不能直接把所有参数设为 DEFAULT，因为可能覆盖维护前的自定义配置。若期间其他管理员修改了配置，应先协调，不能盲目覆盖整个原配置快照。

本方案不自动预约维护或执行重启。执行时需重新核对现场状态及窗口授权。

# Xiya 对接 WMS：中国发订单拉取与接收回执

更新日期：2026-10-13

适用版本：WMS main，提交 `4bba8e6`
对接方向：**Xiya 主动从 WMS 拉取订单，保存成功后向 WMS 回执。**

## 1. 对接流程

1. Xiya 调用 `GET /api/orders/export` 获取符合中国发条件的订单明细。
2. Xiya 按 **`source + id`** 去重，将订单明细和收件信息保存到自己的系统。
3. 仅对已经成功保存的明细，调用 `POST /api/orders/export/ack`。
4. WMS 记录对应明细的接收确认时间。

一行数据代表一条订单明细。同一个平台订单号可能包含多行，不可只按订单号去重。不同 `source` 下的 `id` 也可能相同。

**当前实现限制：回执成功不代表该明细会从后续拉单结果中消失。拉单接口未按回执时间过滤，符合其他条件的已回执明细仍可能再次返回。Xiya 必须持久保存 `source + id` 去重记录，避免重复建单、重复发货。**

## 2. 地址与认证

正式入口使用 HTTPS：

```text
https://wms.fulangke.cn/api
```

| 用途 | 方法 | 完整地址 |
| --- | --- | --- |
| 拉取中国发订单明细 | GET | `https://wms.fulangke.cn/api/orders/export` |
| 确认成功接收的明细 | POST | `https://wms.fulangke.cn/api/orders/export/ack` |

两个接口均使用 WMS 的第三方 API Key，不需要登录 Token：

```http
x-api-key: YOUR_THIRD_PARTY_API_KEY
Accept: application/json
```

回执请求还需设置：

```http
Content-Type: application/json
```

密钥由 WMS 方单独提供，对应配置项 `THIRD_PARTY_API_KEY`。它与 WMS 调用 Xiya 接口使用的 `XIYA_EXPORT_API_KEY` 用途不同，不可混用。本文不包含真实密钥。

兼容 Query 参数 `?apiKey=...`，建议统一使用请求头。Header 和 Query 同时存在时，以 Header 为准。不要继续使用历史文档中的公网 IP `:3000` 地址。

## 3. 拉单接口

```http
GET /api/orders/export
```

无需请求体。当前没有分页、日期范围、平台或店铺筛选参数；一次返回全部符合条件的明细。

### 3.1 返回范围

| `source` | 来源 | 基础筛选条件 |
| --- | --- | --- |
| `rakuten` | 乐天订单 | WMS 发货状态为未发送，且尚未登记运单号 |
| `amazon` | 亚马逊订单处理数据 | 尚未登记运单号，排除 `sourceKind=sp_api` 的看板数据 |
| `manual` | 手动订单 | 尚未登记运单号；平台可能是 Amazon、Rakuten、Tiktok 等 |

基础筛选后，还必须满足以下任一条件：

- `dispatchMode` 为 `china_pending` 或 `china_no_stock`；
- `fulfillmentMode` 为 `xiya_api`，且不在有效的海外仓拣货批次中。

明确已切换为中国发的明细优先按中国发处理。日本发明细不会仅因调用本接口而转成中国发。本接口不会登记运单号，也不会发送邮件。

数据按创建时间升序返回，不应依赖创建时间相同的明细之间的顺序。`total` 为本次返回的**明细行数**，不是去重后的订单数。

### 3.2 调用示例

```bash
curl --request GET \
  'https://wms.fulangke.cn/api/orders/export' \
  --header 'Accept: application/json' \
  --header 'x-api-key: YOUR_THIRD_PARTY_API_KEY'
```

### 3.3 成功响应

| `exportedAt` | string | 本次导出时间，ISO 8601，`Z` 表示 UTC |

| `rows` | array | 订单明细列表，可能为空 |

| `商品名` | string/null | 订单中的商品名称 |

## 4. 接收回执接口

```http
POST /api/orders/export/ack
```

### 4.1 请求体

```json
{
  "items": [
    { "source": "rakuten", "id": "123" },
    { "source": "amazon", "id": "456" },
    { "source": "manual", "id": "901" }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `items` | array | 是 | 至少一条；仅包含已成功保存到 Xiya 的明细 |
| `items[].source` | string | 是 | 必须为 `rakuten`、`amazon` 或 `manual` |
| `items[].id` | string | 是 | 原样传入拉单结果中的 `id`，推荐十进制字符串 |

接口也兼容数字 `id`，但大整数可能丢失精度，接入时统一使用字符串。当前代码未设置回执条数上限，建议按实际成功保存的批次提交。

### 4.2 请求示例

```bash
curl --request POST \
  'https://wms.fulangke.cn/api/orders/export/ack' \
  --header 'Content-Type: application/json' \
  --header 'x-api-key: YOUR_THIRD_PARTY_API_KEY' \
  --data '{"items":[{"source":"manual","id":"901"}]}'
```

### 4.3 成功响应

当前 HTTP 成功状态为 `201`（POST 默认状态），JSON 使用 WMS 标准包装。应判断 HTTP 为 2xx 且 `code=0`，读取 `data`。

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "acknowledgedAt": "2026-10-13T06:01:00.000Z",
    "requestedCount": 3,
    "rakutenCount": 1,
    "amazonCount": 1,
    "manualCount": 1
  },
  "requestId": "example-request-id",
  "timestamp": "2026-10-13T06:01:00.100Z"
}
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | number | `0` 表示本次接口处理成功 |
| `message` | string | 成功时为 `OK` |
| `data.acknowledgedAt` | string | 本次接收确认时间，ISO 8601 |
| `data.requestedCount` | number | 请求中传入的条数，包含重复项 |
| `data.rakutenCount` | number | 本次新确认的乐天明细数 |
| `data.amazonCount` | number | 本次新确认的亚马逊明细数 |
| `data.manualCount` | number | 本次新确认的手动订单明细数 |
| `requestId` | string/null | 请求追踪号，失败排查时保留 |
| `timestamp` | string | 服务端响应时间，ISO 8601 |

### 4.4 重复调用与计数

- 同一请求中的相同 `source + id` 会去重后处理。
- 已确认过的明细不会再次增加计数，也不会更新首次确认时间。
- 不存在、不再符合回执条件的 ID 会被跳过；目前不会逐项返回成功/失败 ID。
- 因此，即使 `code=0`，实际计数总和也可能小于 `requestedCount`，甚至为零。不能把计数不足一概判断为保存失败。
- 同时包含有效和无效 `source`/无法解析的 `id` 时，参数校验失败，不写入本批确认标记；通过校验的可确认记录在事务中更新。
- 这个回执只确认**接收**，不表示已发货、已签收，也不会自动登记运单号。

## 5. 错误响应

两个接口失败时均使用标准错误包装，与 GET 的成功格式不同：

```json
{
  "code": 401,
  "message": "第三方接口密钥无效",
  "data": null,
  "requestId": "example-request-id",
  "timestamp": "2026-10-13T06:02:00.000Z"
}
```

| HTTP / `code` | 场景 | `message` 示例 | 处理建议 |
| --- | --- | --- | --- |
| 400 | 回执 `items` 为空或不是数组 | `请至少提供一条回执记录` | 修正请求体 |
| 400 | 回执来源无效 | `items[0].source 只支持 rakuten、amazon 或 manual` | 原样使用拉单返回的 `source` |
| 400 | ID 无法解析 | `items[0].id必须为有效数字ID` | 原样使用拉单返回的字符串 ID |
| 401 | 密钥缺失或不匹配 | `第三方接口密钥无效` | 核对 WMS 第三方密钥，避免无效重试 |
| 503 | WMS 尚未配置第三方密钥 | `未配置第三方接口密钥` | 联系 WMS 方配置 |
| 500 | 服务端或数据库错误 | `服务器内部错误` / `数据库错误` | 保存 `requestId`，退避重试并联系 WMS 方 |

网络超时、连接中断时，Xiya 应保留本地保存结果及待回执队列，恢复后重试回执，不要重新创建同一订单明细。

## 6. Xiya 接入建议

1. 在本地为 `(source, id)` 建唯一约束，作为接收去重键。
2. 同一平台订单号多明细需要按行保存，可按 `source + 注文ID` 分组展示，不能合并后丢失 WMS 明细 ID。
3. 接收时核对产品 ID、数量及收件信息；字段缺失的行进入人工处理，不能仅凭接口返回就安排发货。
4. 已成功保存的行进入持久化待回执队列；保存失败的行不回执。
5. 回执超时可以用相同 `source + id` 重试，重试后新增确认计数为零不一定代表失败。
6. 后续 GET 再次返回已保存行时，按本地唯一键识别，不重复建单或发货；如要处理订单信息变更，应单独核对 `updatedAt` 和字段变化。
7. 暂无增量游标、数据锁定、取消通知或逐行回执查询接口，不把重复出现或消失的明细直接解释成新订单或取消订单。
8. 平台名、店铺名是显示和业务信息，不是固定编码。店铺改名后，历史与新记录名称可能不同，应以 `source + id` 维持接收身份。

## 7. 联调验收清单

- 正确密钥能拉取，错误密钥返回 `401`。
- 支持 GET 裸 JSON 与 POST 标准包装两种成功格式。
- 支持 `rakuten`、`amazon`、`manual` 三种来源。
- 一个业务订单多明细、不同来源同 ID 均不会被错误合并。
- 大整数 ID、邮编、电话号码保存为字符串，前导零不丢失。
- 保存成功后才回执；部分保存失败时只回执成功行。
- 回执重试及重复 GET 不会导致重复建单或重复发货。
- `rows=[]` 作为正常空结果处理；`null` 字段与空字符串分别保留。

## 8. 版本说明

本说明按当前已提交的接口实现整理，未向生产环境发送真实订单或回执。本次仅整理文档，不修改接口行为。

与 2026-04-22 旧文档相比：正式地址改为 HTTPS 域名；来源补充 `manual`；回执响应补充 `manualCount`；说明 POST 成功状态为 `201`；更正“回执后拉单不再返回”的旧说明，明确当前必须由 Xiya 持久去重。

## 2026-10-26：乐天订单拉取锁定

乐天明细在 GET 拉单返回前会先持久化 `xiya_pulled_at`，与接收回执时间 `xiya_exported_at` 分开记录。拉取锁定或接收回执任一存在，即禁止人工切日本发。若人工切日本发先完成，拉单的条件更新失败，该明细不会出现在返回结果中。

网络超时也保留拉取锁定，不自动解锁；Xiya 可重新拉取，并继续按 `source + id` 去重及回执。该变更不改变接收回执含义，也不改变亚马逊及手动订单流程。上线前已经拉取但未回执的历史请求无法通过新增字段追溯，部署时应暂停拉取，等待在途请求完成并核对回执，再恢复切换与拉取。

# 2026-10-28 云盘使用率增长调查

调查时间：日本时间 08:28–08:35。对象：DGAZ-wms，系统分区 `/dev/vda3`。本次为只读生产调查；未清理文件、修改数据库配置、重启服务或部署。

## 结论

10 月中旬以来持续上涨的主要原因是：乐天定时订单处理中的物流状态轮询，持续更新带有大 JSON 字段的订单宽表；MySQL 使用 `ROW + FULL` 二进制日志，记录更新前后的完整行，并在本机保留 30 天。大量重复更新产生的二进制日志逐日累积，已经占用 15.68GB（14.60GiB）。

直接证据包括：四份跨日期日志样本的约 96%–99.8% 字节属于 `rakuten_order_records` 行事件；最近两小时更新的 286 条订单中，280 条更新时间与物流查询时间吻合，6 条与 RMS 同步时间吻合。近期主写入来源因此指向物流轮询，订单导入也有额外重复写入路径。

这不等于所有历史日志均来自物流轮询：样本不是全量统计，时间字段匹配也不是 SQL 调用追踪。10 月 14 日首次样本含一次集中写入，不能全部解释为日常轮询。

### 对应代码

- `apps/api/src/rakuten-rms-api/rakuten-order-scheduler.service.ts:66`：每轮订单处理执行物流状态同步。
- `apps/api/src/orders/orders.service.ts:9388`：`persistRakutenTrackingStatus` 按运单更新相关订单行，无状态差异条件；每次都写入 `trackingCheckedAt = new Date()`（9401 行）。同一运单多条商品行会一起更新。
- `apps/api/src/rakuten-rms-api/rakuten-rms-api.service.ts:1101`：业务字段未变化的导入计划也先执行 `applyOrderPlan`，然后才统计为 unchanged。
- 同文件 1715 行：更新整条订单写入数据；1784 行包含 `rawPayload`，1793 行刷新 `rmsLastSyncedAt`。
- 同文件 1094 行和 1923 行：冻结订单、重复人工处理观察也可能仅刷新同步时间。

因此，即使订单或物流业务状态没有变化，时间戳更新仍会产生真实 UPDATE。`FULL` 会记录更新前后全部列，大 JSON 随之重复进入 binlog。MySQL 官方说明见 [行镜像配置](https://dev.mysql.com/doc/mysql-replication-excerpt/8.0/en/replication-options-binary-log.html)。

## 对策及优先顺序

### 1. 先释放已有日志占用，并明确恢复窗口

建议在核实备份可恢复、复制/CDC 依赖及恢复窗口后，将本机 binlog 保留期调整为 7 天；如果需要 30 天恢复能力，将更早日志可靠归档到独立存储后再清理。本机备份卷不能替代独立备份。

现场未发现配置的上游复制通道，活跃 Binlog Dump 连接也为 0；这只代表采样时状态，不能排除离线消费者或之后重连的副本。应核对实际备份/复制依赖后确定可清理边界。

按文件 mtime 严格早于调查时刻 7 天估算，候选日志约 **7,647,201,195 字节（7.65GB / 7.12GiB）**。最终应以 `SHOW BINARY LOGS` 及有效恢复链确定边界，通过 MySQL `PURGE BINARY LOGS` 清理，不能直接删除数据目录中的日志。若该候选量全部可清理、期间没有其他增长，使用率预计可从 89% 降到约 70%，以清理后 `df` 为准。

需要同时持久化过期策略；只清理一次仍会继续积累。官方依据：[二进制日志维护](https://dev.mysql.com/doc/refman/8.0/en/log-file-maintenance.html)、[PURGE BINARY LOGS](https://dev.mysql.com/doc/refman/8.0/en/purge-binary-logs.html)。

### 2. 优先减少物流轮询的宽表写入

- 将每次查询的检查时间、错误和当前物流状态放到独立的轻量物流状态表，按运单保存；只有业务状态变化时更新订单字段，避免一张运单的多条商品行反复记录整个订单。
- 保持前端“最后查询时间”正确；不能为了减量直接丢弃这个时间字段而改变业务含义。
- 对终态且清关信息完整的运单停止自动查询；对历史无效、长期失败或信息不完整的运单采用退避和人工处理，避免一直固定 20 分钟轮询。保留必要的清关补查和异常恢复路径。
- 导入中未变化的订单不重写整条 `rawPayload`；同步新鲜度用轻量元数据记录，仍保留回滚、人工接管及订单变更检测能力。

这些是待实现方案；本次未改动业务代码。

### 3. 评估 MINIMAL 行镜像，降低日志放大

在确认恢复工具、CDC 和复制兼容后，评估 `binlog_row_image=MINIMAL`。对物流查询这类只更新少数字段的操作，可避免把未涉及的大 JSON 列重复写入日志。它不能代替应用侧减少无效 UPDATE；SQL 本身若仍显式更新大字段，收益会受到限制。

该变量有会话级值，修改全局/持久配置后，已有应用连接池需要按计划更新连接并验证实际会话配置；不要宣称全局设置后所有现有连接立即生效。先做隔离恢复演练，再进行受控配置变更。

### 4. 配套容量与部署治理

- 核实回滚需要后清理未使用镜像；Docker 当前报告约 2.395GB 可回收，不能把它当成一定能全部安全释放的保证。保留运行镜像和必要回滚版本，不清理生产卷。
- 配置磁盘使用率 75%/85%/90% 分级告警，并记录可用字节、每日 binlog 新增量和主要目录增量。建议剩余空间低于 5GiB 或预测不足 7 天时告警。
- 部署前增加可用磁盘检查。当前资源检查脚本主要检查内存和 PSI；镜像导入需要额外空间余量。
- 将 journal/atop 留存纳入明确上限，补齐 Redis 轮转。其收益小于 binlog 整治，应按优先级处理。
- 如业务要求长期本机留存，评估扩容或独立数据盘；扩容用于提供余量，持续写入仍需治理。

## 验收标准

1. 清理后记录 `df -B1`、binlog 总量、剩余日志清单和恢复边界；确认订单、物流、邮件等流程正常。
2. 新旧方案对照一个完整业务日，比较 binlog 新增字节与订单表 UPDATE 次数，按实际降幅验收，不预先承诺固定压缩比。
3. 验证物流状态变更能正常推动邮件/出货流程，未变化的查询仍显示正确检查时间，异常运单可重试，人工接管与回滚不受影响。
4. 从独立备份及保留日志恢复到隔离数据库，验证实际恢复窗口。

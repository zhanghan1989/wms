# 批量更新库存内存调查

日期：2026-10-06。范围：本地代码审查及不连接数据库的内存复现；未采集线上堆快照，未修改业务代码。

## 结论

已确认两个可以复现的机制：看板刷新保留多份完整快照造成存活堆逐次增加；大批量审计处理产生临时分配峰值，回收后进程 RSS 仍可能维持高位。线上各因素的贡献需结合具体导入规模和进程指标判断。

## 1. 更新成功后强制刷新看板，旧快照继续驻留

调用链：`apps/api/public/app.js:18434` 的提交处理在导入完成后并行执行 `loadInventory()`、`loadAudit()`、`loadOverviewDashboard({ forceRefresh: true })`。

`loadOverviewDashboard` 请求同时携带 `paged=true` 和 `refresh=true`。`InventoryController` 先取得完整看板，再调用 `dashboardFirstPages` 截取首页。

`apps/api/src/inventory/dashboard-pages.ts` 的模块级 `snapshots` Map 强引用完整看板。每次重算返回新对象，因此相同看板参数也会创建新快照。快照有效期 10 分钟，最多 12 份；到期清理只在 `dashboardFirstPages` 被再次调用时执行。`dashboardPage` 对过期快照仅抛错，并不删除。没有后续请求时，过期对象仍会驻留。WeakMap 不能抵消 snapshots Map 的强引用。

本地实际调用 `dashboardFirstPages`，每次构造含 50,000 条简化产品记录的独立看板，再强制 GC：

| 刷新次数 | 堆占用 MiB |
| --- | ---: |
| 0 | 25.8 |
| 1 | 31.8 |
| 3 | 44.0 |
| 6 | 62.3 |
| 12 | 99.0 |
| 14 | 99.0 |

每个响应只返回 30 条列表记录，完整列表却仍存活。数据是合成的，不代表线上每份快照大小。此机制有 12 份上限，不是无限泄漏；共享快照池也包含其他用户和参数的看板请求。

另有 `dashboard-cache.ts` 保存最多 12 个参数键的当前看板。相同键刷新会替换值，因此它自身不会按同键刷新次数一直增加，但分页快照池会保留此前的对象。两者可能引用同一对象，不能简单将数量相加。

## 2. 导入本身产生多层全量数据和审计峰值

`inventory.service.ts:2607` 对 Excel 使用 `XLSX.read`，未限制读取工作表；之后第一张表全部转换为 JSON，再构造解析结果。导入方法又构造 rows、targets、inventoryRows、库存 Map、adjustItems 等结构。

`findMasterProductBoxInventoryByPairs` 把所有库存对一次转为 OR 条件，没有分块。整个导入在最长 120 秒的单一事务中处理。

每条实际变更构造两条审计记录（箱和产品）。`AuditService.createMany` 对所有 payload 一次 map，再对 before/after 和 changedFields 做 JSON 规范化，最终一次提交全部审计记录。

本地复现使用真实 AuditService、模拟 createMany 数据库出口，并在出口追加普通 JSON 序列化来模拟传输分配；不是 Prisma 引擎或 MySQL 实测。20,000 条模拟变更产生 40,000 条审计 payload：

| 阶段 | heapUsed MiB | RSS MiB |
| --- | ---: | ---: |
| 初始 | 45.2 | 207.3 |
| 构造 payload | 62.8 | 210.6 |
| 真实审计规范化后 | 88.1 | 235.4 |
| 模拟 JSON 编码后 | 131.8 | 367.3 |
| 释放并强制 GC 后 | 45.2 | 325.2 |

重复三轮后，GC 后堆仍约 45.3 MiB，RSS 约 358.4 MiB。说明至少这个隔离路径没有持续保留审计 payload，但 RSS 不一定随存活堆立即恢复。

20,000 行有效 Excel（压缩文件约 0.92 MiB）的真实解析使 heapUsed 从 54.9 增至 79.4 MiB，回收后恢复。解析测量前已经构造测试工作簿，所以它是阶段增量，不能视为整个导入峰值。

上传入口 `FileInterceptor('file')` 无本地文件大小限制；未发现全局 MulterModule 限制。解析和业务处理也无导入行数上限。并发导入可进一步放大占用。

## 3. 看板重算与库存刷新额外制造峰值

`getOverviewDashboardByProduct` 并行读取全量启用产品、SKU、FBA 快照明细、近 90 天乐天订单及 Amazon 非 SP-API 发货记录，然后建立多组 Map、Set 和中间数组。页面分页发生在完整计算之后，不能降低计算阶段内存。

`loadInventory` 同时获取全量 SKU 和库存汇总。故少量行的导入也能触发与全库规模有关的看板重算，不能只根据上传文件大小估算开销。

库存减少时逐条调用 `assertStockAvailable`，重复读取对应产品的箱库存及预占明细。同一产品涉及多个箱时重复处理，主要增加事务时间和临时分配，并非已证实的持久引用泄漏。

## 处理优先级

1. 调整分页快照生命周期：主动删除过期快照，并根据实际列表大小或字节预算限制保留量；要兼顾已有分页会话，不能直接删除所有旧快照。
2. 将审计 payload 的构造、规范化、写入分块，并维持在同一事务内以保留原子性；仅在 AuditService 内切块仍会保留调用方完整 payload 数组。
3. 对库存对查询分块；只解析必要工作表，设置文件、行数和并发限制。
4. 优化更新后的刷新范围：可先更新库存相关摘要、延后非当前页面的完整看板重算；销量数据与库存数据拆开缓存，降低每次库存更新的重复计算。

## 线上确认所需证据

需要明确观测对象是 API 进程、浏览器还是数据库，以及每次导入行数。按上传前、解析后、审计前后、事务结束、看板重算结束记录 rss、heapUsed、external、arrayBuffers 和请求 ID；在多次导入后对比堆快照，确认分页 snapshots 对象的保留大小。若 GC 后 heapUsed 随刷新次数增加到平台期，应优先检查快照池；若 heapUsed 回落但 RSS 维持高位，则还需检查运行时及原生内存。未取得这些数据前，不应把线上增长全部归因于单一机制。

## 优化实施与复测（2026-10-06）

已修改：

- 分页快照只保存 top/no-sales 两个列表，不再引用整个看板对象；每份快照设置 10 分钟自动释放定时器，淘汰时同时取消定时器。
- 快照池保留原有 12 份上限，同时限制总保留行数为 100,000；超限按创建顺序淘汰旧快照。单份快照超过预算时仍保留最新一份以保证当前分页可用。这是行数预算，不是精确字节预算；提前淘汰的旧分页会提示刷新。
- 批量库存审计每 500 条构造、规范化和写入，调用方不再生成完整 2N 条 payload 数组；所有批次仍使用原事务客户端。
- 批量导入库存对查询每 500 对执行；其他调用保留原查询方式。
- Excel 只解析第一张工作表，保留原导入格式和校验规则。

使用相同的 50,000 行快照复现脚本：修改前第 12 次刷新后堆占用约 99.0 MiB；修改后第二次起稳定约 38.0–38.1 MiB，后续刷新不再累积到 12 份。以上为本地合成数据测量，不是线上峰值承诺。

新增回归验证覆盖：501 条变更完整生成 1,002 条审计、三批分别为 500/500/2；查询按 500/1 分块；批次失败传出事务回调且停止后续批次；第一张表解析；到期无需新请求自动释放快照；行数预算淘汰与最新快照末页可用。线上 MySQL 原子性仍需数据库集成环境验证。

尚未改动看板全量计算算法、页面更新后的刷新策略、上传大小与并发限制；这些仍可能贡献峰值，应根据上线后指标继续评估。

验证结果：全量测试 37 个套件、363 项通过；19 项 MySQL 集成测试因未设置测试数据库跳过。类型检查、构建与差异格式检查通过。代码尚未部署。

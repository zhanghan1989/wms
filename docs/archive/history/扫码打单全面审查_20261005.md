# 扫码打单全面审查（2026-10-05）

本文记录优化前的审查发现；后续修复及验证见 [扫码打单优化说明](./扫码打单优化_20261005.md)。

审查对象是审查当时工作区中的扫码打单实现，包含上一轮尚未部署的修复。覆盖 PDF 上传和面单匹配、肩带成品码/本体码替代扫码、无码配件确认、浏览器/服务器直打/打印代理、重试、补打、多工作站操作及批次完成。

结论：仍有需要修复的问题，建议先补齐高优先级问题，再部署上一轮改动。当前“成品码或本体码二选一，每件只扫一次”的业务规则保持正确；主要缺口集中在任务状态、工位归属和异常恢复。

## 必须优先修复

### 1. 高：缺少订单号时，错误订单的 PDF 仍可能通过匹配

当前先查找订单号；没有命中时，降级为“包含全部产品 ID、包含收件人姓名且候选唯一”。如果上传另一订单的面单，而商品和姓名相同，单页批次仍会通过，即使 PDF 中出现的订单号明确属于其他订单。

模拟输入：预期 `EXPECTED-ORDER / SKU / 王小明`，实际 PDF 文字为 `OTHER-ORDER SKU 王小明`，当前函数接受实际页面。该匹配结果随后用于回写快递单号，风险会传播至订单。

建议：优先解析订单号对应的字段；PDF 存在订单号但与预期不符时直接拒绝。缺少订单号的格式要校验更多收件信息，并在无法建立可靠绑定时展示核对结果，不应仅凭商品和姓名自动通过。

位置：[面单匹配](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7490)。

### 2. 高：尚未提交打印的代理任务可直接确认已出纸

`confirmYamatoLocalPrintJob` 对 `pending` 状态普遍放行。打印代理刚入队、尚未领取的任务也能被确认，进而将任务及面单标记为完成；此后代理不会再领取这个任务。

模拟验证：`yamato_label / pending` 经确认后变为 `completed`，面单被标记已打印。

建议：按打印方式分别限制状态转换。代理任务只能在提交回执成功或已明确进入不确定结果核对流程后确认出纸。待领取状态不可确认已出纸；取消未领取任务使用独立操作。

位置：[出纸确认](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7194)。

### 3. 高：不同工作站会复用同一个任务，缺少装包归属

正常打印发现当前页面已有活动任务时直接返回该任务，没有检查请求编号、操作员或工作站是否相同。两个工作站扫描同一商品时都可能进入同一订单的装包和出纸确认流程。确认接口同样没有检查任务归属，其他登录用户可以确认该任务。

模拟验证：A 的任务由 B 的不同请求复用；B 可以登记 A 任务的出纸确认。

建议：增加装包会话和工位归属，在选定订单时占用，明确显示其他工位正在处理。只有同一请求的重试才复用；其他工位应得到占用提示。接管需要独立、可追溯的流程。

位置：[任务复用](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7092)、[出纸确认](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7194)。

### 4. 高：进程中断后，执行中任务可能永久卡住

服务器直打在发送到打印机前创建 `claimed` 任务。进程在该时段崩溃或重启后，重试会提示“正在提交”，出纸确认也拒绝该状态。代理领取后中断且未回报，同样没有心跳、恢复状态或人工核对入口。

模拟验证：直打 `claimed` 任务既无法重试，也无法确认未出纸。前端扫码和待确认记录仅在页面内存中，刷新后无法直接恢复原会话；没有按批次列出异常任务的接口。

建议：增加心跳、超时检测和异常任务列表，将中断任务转为“结果待核对”。确定未发送的任务允许重试，可能已发送的任务必须核对后处理，不能直接按超时自动重打。保存任务 ID 和必要会话信息，支持刷新后恢复。

位置：[直打任务占用](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7092)、[代理领取](/Users/zhanghan/repositories/001-wms-main/apps/api/src/print-agent/print-agent.service.ts:38)、[提交等待](/Users/zhanghan/repositories/001-wms-main/apps/api/public/app.js:13813)。

## 影响操作准确性的问题

### 5. 中：打印期间继续扫码可能静默丢码

按钮处于忙碌状态时，`withBusyButton` 直接返回，不处理下一次扫描。输入框仍可输入；第一笔成功后又会清空输入框，擦掉期间输入的第二个码。

模拟验证：先扫 A 并等待打印，期间输入 B；B 的操作没有执行，A 完成后输入框为空。

建议：忙碌期间明确阻止扫码并给予提示，或把扫描事件放入有序队列。只清除已经消费的输入值；扫描接受、拒绝和完成应有明确的声音或视觉反馈。

位置：[忙碌处理](/Users/zhanghan/repositories/001-wms-main/apps/api/public/app.js:3508)、[扫码提交](/Users/zhanghan/repositories/001-wms-main/apps/api/public/app.js:14012)。

### 6. 中：补打仍在执行时，批次可被确认完成

批次完成只检查面单的 `printedAt`，没有检查活动打印任务。补打保留首次打印时间，因此即使新的补打任务尚未完成，批次仍可能被标记作业完成。

模拟验证：面单已有打印时间、存在一个活动补打任务，批次仍被标记完成。

建议：批次完成同时检查活动任务和结果待核对任务；检查及状态更新应在同一事务内，与新建打印任务采用一致的锁定规则。

位置：[批次完成](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:1164)。

### 7. 中：快递单号提取会取到其他同格式号码

目前取 PDF 中第一个 `4-4-4` 数字串，找不到则取第一个 12 位数字；未确认号码来自快递单号字段。模拟文字先出现商品 ID `1234-1111-2222`，随后才出现快递单号 `9999-8888-7777`，当前提取前者。

上传时只检查号码是否存在，未检查不同订单的面单是否出现重复快递单号。

建议：结合快递单号字段标识或位置提取；存在多个候选时阻止自动回写。对不同订单出现相同快递单号进行检查和提示。使用实际 Yamato PDF 验证文字顺序和字段定位。

位置：[号码提取](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:7946)、[上传检查](/Users/zhanghan/repositories/001-wms-main/apps/api/src/orders/orders.service.ts:6800)。

## 进一步优化

1. **增加面单与包裹的反向核对。** 出纸后扫描面单快递单号，与当前装包订单比较，减少正确面单贴到错误包裹的风险，也比单纯点击“已出纸”提供更明确的核对依据。
2. **提供统一任务面板。** 区分待领取、提交中、已提交待出纸、结果待核对、已完成、失败，显示工位、打印机、快递单号、时间和允许的恢复操作。当前多个状态叠加在 `claimed` 和 JSON 字段中，难以直接理解。
3. **明确打印方式和路由。** 打印代理按商品配置选择打印机，服务器直打使用全局配置。切换方式前显示实际目标打印机，避免输出位置改变而操作员不知情。
4. **减少重复 PDF 处理。** 当前每次打印读取整个批量 PDF，再加载和提取单页。上传后缓存经验证的单页，按需读取；扫描预览只返回必要候选信息。文件写入尽量放在长事务之外，同时保持任务在文件准备完成前不可被领取。
5. **完善输入和文件限制。** PDF 上传目前仅限制文件个数，没有该接口的单文件大小限制；增加总大小、页数和解析时间限制。请求编号应有浏览器兼容处理，避免旧浏览器或非安全访问环境中 `crypto.randomUUID` 不可用。
6. **验证备注版面。** 括号内材料总量与组装窗口用量应明确区分，使用真实合并订单面单确认长备注不会截断关键 ID 和数量。
7. **补充验证层次。** 除函数测试外，加入 HTTP 接口状态转换、真实数据库并发、真实 PDF、代理重启与网络断连测试，以及一次现场打印验收。

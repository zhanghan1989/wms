# WMS 逻辑审查与优化方案

审查日期：2026-09-22。代码基线：`a20a8b3`。

## 范围与验证边界

重点检查登录鉴权、用户管理、入库、库存调整、移箱、FBA 补货和海外仓拣货之间的调用及数据关系。本次为重点代码审查，不是全项目无漏洞认证；没有连接生产数据库、调用生产业务接口或修改业务代码。

- 现有测试：26 个测试套件、267 个测试全部通过。
- 类型检查：`npm run lint` 通过；项目该命令实际执行 TypeScript 类型检查。
- 额外隔离验证：直接调用现有代码，以内存替身代替数据库，验证了令牌校验不读取用户状态、管理员自提权、零实收入库未保存实收量、纯产品调整缺少流水、拣货计划不读取 FBA 预占这五个行为。
- 并发问题依据读写顺序、锁及更新条件判断；尚未通过真实 MySQL 并发集成测试复现，不代表线上已经发生。最终表现可能是覆盖、重复流水或死锁回滚，取决于事务交错和隔离级别。

## 发现与修复

### 1. P1：普通管理员可以给自己设置系统管理员角色

证据：`apps/api/src/users/users.controller.ts:16` 允许 admin 管理用户；`users/dto/update-user.dto.ts:13` 接受整个 Role 枚举；`users/users.service.ts:147` 直接接受目标角色，只校验该角色是否启用，没有校验操作者是否有权授予。创建用户路径也接受该角色。前端 `public/app.js:1699` 隐藏 system_admin 选项不能约束 API。

触发：非保留用户名的 admin 向自身用户更新接口提交 system_admin。隔离验证显示 DTO 校验通过，服务写入成功。这个区别具有实际业务影响：`sku-edit-requests/sku-edit-requests.service.ts:453` 允许系统管理员越过工厂部门限制确认产品变更。

修复：后端建立明确的角色授予规则。普通管理员不能创建、授予或修改系统管理员，也不能通过修改自身部门绕过需要隔离的审批权限。系统管理员保护应基于角色和权限，而不是仅检查用户名是否等于 admin。创建、修改、重置密码均须应用目标用户保护规则。

验收：直接请求 API 的 admin 自提权、创建高权限用户、修改其他系统管理员应被拒绝；合法用户管理仍能完成。

### 2. P1：禁用、降权、改密及退出后，旧令牌缺少撤销机制

证据：`apps/api/src/auth/jwt.strategy.ts:26` 验证后直接返回令牌内的 role，没有读取账号状态、当前角色或会话版本；`auth/auth.controller.ts:31` 退出仅返回成功。默认令牌有效期是 12 小时，见 `auth/auth.module.ts:19`。

触发：已登录用户被禁用或降权，仍使用旧令牌请求只依赖 JwtAuthGuard/ RolesGuard 的业务接口。`/auth/me` 自身检查数据库并不能保护其他业务接口。密码重置或退出也没有使已签发令牌失效。

修复：鉴权时读取有效用户和当前权限；增加 sessionVersion 或可撤销会话记录。禁用、改密、重置密码、权限变更时撤销相关会话；退出撤销当前会话。若缓存权限，必须同步失效缓存。MFA 和强制改密状态也应结合服务器当前状态验证。

验收：上述操作后旧令牌请求业务接口被拒绝；降权用户不能继续使用原管理员权限。

### 3. P1：库存先读后覆盖，跨单据并发存在丢失更新风险

证据：`apps/api/src/inventory/inventory.service.ts:4178` 读取库存并计算调整后数量，4218 行写回绝对值；3932、3951 行的公共写入函数没有版本条件。FBA 出库 4714 行同样按读取的旧值计算。移箱 597 行起、批量入库 `batch-inbound/batch-inbound.service.ts:880` 也有类似模式。

触发示例：同箱同产品库存 10，两次调整都先读到 10，分别减 3 和减 4，写回 7 和 6；若都提交，期望值 3 被覆盖成 6 或 7。事务保证一次操作整体提交，不自动保证先读后写期间库存没有变化。已有的单据锁也不能串行化其他单据对同一库存的更新。

另一处风险是总库存回算：`inventory.service.ts:2158` 将箱库存聚合后覆盖 masterProduct.stockQty，不同箱子同时更新同一产品时，聚合快照可能陈旧，导致总库存与箱库存不一致。

修复：统一库存变更入口。扣减使用带 `qty >= 扣减量` 条件的原子递减并检查影响行数，增加使用原子递增；绝对数量调整使用版本校验。所有写入路径按一致顺序取得产品/库存锁，并保证读取发生在取得正确锁之后。总库存采用同事务原子增量，或在统一产品锁下基于最新数据回算。新增库存行和死锁重试也必须纳入处理。

验收：真实 MySQL 中并发调整、FBA 出库、入库、移箱后，箱库存不丢失、不为负，总库存等于箱库存之和，失败事务不留下流水。

### 4. P1：FBA 状态迁移没有并发保护，可重复记账或覆盖终态

证据：`apps/api/src/inventory/inventory.service.ts:4641` 出库事务先普通读取补货单，最后 4809 行仅按 id 更新为 outbound。确认 4486 行起、重开 761 行起也未锁定补货单，更新时没有带旧状态条件。

触发：两个出库请求同时读到 pending_outbound，可同时通过前置检查并创建流水。又如确认数量与出库交错：确认请求先读取旧状态，出库完成后，确认请求仍可能把状态覆盖回 pending_outbound，允许再次出库。

修复：在事务最开始按固定顺序锁定全部补货单，锁内重新校验数量和状态；或用带旧状态/版本的条件更新抢占处理权。状态迁移、库存变更、流水必须同事务完成。已完成的重复请求返回原结果。为每条出库明细设置稳定业务幂等键，不能仅依赖前端防双击。

验收：同一补货单并发提交 20 次，只有一份库存变更和流水；确认、删除、重开与出库交错不能覆盖不允许的状态。

### 5. P1：FBA 和海外仓拣货的库存预占彼此不可见

证据：`inventory/inventory.service.ts:4376` 起仅统计 FBA 活跃申请；`orders/orders.service.ts:6080` 起仅统计海外仓活跃拣货计划。后者从箱实存中减去自己的预占，没有减 FBA 预占。

触发：箱内库存 10，FBA 已预占 8，海外仓订单仍可能建立待拣 8 的计划；这个问题不需要并发请求。两边总预占 16，实际只有 10，后执行的出库会遇到库存不足。手工扣减也未统一检查预占。

修复：短期统一可用量查询，同时扣除 FBA、成品拣货和 BOM 材料预占；中期建立预占记录，包含来源单据、产品、箱位、数量及状态。申请、确认改量、取消、出库均原子创建、调整、释放或消耗预占。盘亏需要显式标识受影响的预占并触发处理，不能静默破坏承诺库存。

验收：库存 10、FBA 预占 8 后，新增拣货 8 必须拒绝或明确缺货；反向顺序结果一致；BOM 共用材料也不可超占。

### 6. P2：批量入库实际收货数量没有持久化，刷新后显示原数量

证据：`batch-inbound/batch-inbound.service.ts:868` 与 916 行只保存 confirmed 状态和时间；`prisma/schema.prisma:300` 的 BatchInboundItem 没有实收字段；详情仍返回 item.qty。前端 `public/app.js:10113` 将实际数量输入框也设置为 item.qty。

触发：应收 10、实收 8，库存增加 8，但刷新详情后实收栏变回 10；实收 0 时也把明细标为已确认，却没有保存 0。后者已经通过隔离调用验证。正数实收虽在操作审计中留有增量，也不等于单据明细保存了实收事实。

修复：明确保存 expectedQty、actualQty、差异原因、确认人和确认时间；已确认页面只读取持久化的 actualQty。零实收也要记录差异及确认审计。历史数据只能按可核验日志回填，无法确定的保留未知，不能直接把应收量当成实收量。

验收：实收 0、8、10 三种情况在提交、刷新、再次查询和导出后保持一致；重复确认不重复加库存。

### 7. P2：按产品 ID 手工调库存时漏记库存流水和调整明细

证据：`inventory/inventory.service.ts:4193` 将调整明细和 stockMovement 创建都放在 `if (sku)` 内；仅提供 productId 时 sku 为 null，库存仍在 4218 行被更新。StockMovement 的 skuId 本身允许为空，可以记录产品维度流水。

触发：仅填写产品 ID、箱号和调整量。隔离验证中库存从 10 减至 8，但流水数和调整明细数均为 0。操作审计仍存在，因此不是完全没有日志；问题是库存流水不能完整解释库存变化。普通入库、批量入库和移箱路径也需要按同一标准补齐流水。

修复：每次库存变更无条件生成产品维度流水，skuId 作为可选信息。调整明细模型支持 productId；移箱写出、入两笔关联流水。业务单据、余额及流水同事务提交，定期核对“期初 + 流水 = 当前库存”。

验收：有 SKU 和无 SKU 的调整均能从单据追踪至流水及余额；失败和重复请求不会产生孤立或重复流水。

## 实施顺序

1. **先修权限边界**：角色授予规则、有效账号校验和会话撤销。改动可独立验证。
2. **修库存写入与 FBA 状态迁移**：先建立统一锁顺序、原子更新和业务幂等，再迁移入库、调整、出库、移箱全部入口。不能仅修某一个入口后认为并发问题已解决。
3. **统一预占**：FBA、海外仓成品、BOM 材料共用可用库存规则，并处理取消、改量和盘亏。
4. **补齐事实记录**：实收字段、产品维度调整明细、完整库存流水；先做只读对账，再人工确认历史差异如何修复。
5. **逐步拆分大模块**：orders.service.ts 约 1.14 万行、inventory.service.ts 约 4800 行、前端 app.js 约 2.1 万行。按库存、预占、拣货、发货、平台同步边界拆分，优先抽取跨入口必须一致的规则。读列表增加分页，盘点大型查询与索引，再依据执行计划优化，避免未经测量直接改索引。

## 修复后的最低回归清单

| 场景 | 必须保证 |
| --- | --- |
| 禁用、降权、改密、退出 | 旧权限/会话不能继续使用 |
| admin 直接调用角色更新 API | 无法授予 system_admin 或绕过审批边界 |
| 同箱同时加减、不同箱同产品更新 | 无丢失更新，总库存与箱库存一致 |
| FBA 重复出库及与改量/重开交错 | 合法状态迁移，库存和流水只生效一次 |
| FBA 与拣货、BOM 混合占用 | 总预占不超过可分配库存 |
| 差异收货与零收货 | 应收与实收分别持久化，刷新/导出一致 |
| 无 SKU 的产品调整、入库、移箱 | 库存流水完整且与余额可对账 |

现有单元测试通过只能说明已有断言满足，不能覆盖上述缺失场景。并发验收需要隔离的真实 MySQL 测试库，并使用与部署一致的事务隔离配置。

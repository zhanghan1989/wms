# 亚马逊三店同步优化

日期：2026-10-15。本次发布范围为亚马逊三店同步优化及每日同步时间调整，不包含乐天库存自动同步功能，无需新增数据库迁移。开发验证没有连接生产重新执行同步或生成快照。

## 行为变化

- 保持店铺 ID 顺序逐店同步，以及原有订单/库存接口的分页处理；补充全部店铺同步的进程内运行保护，避免直接调用时重复并发。
- 每次定时同步只有在本轮所有店铺均成功完成时才生成销售快照。失败、部分完成或被其他任务占用时，保留上一份快照。单店同步失败仍继续处理其余店铺。
- 销售快照按 SKU、近 90 天已发货/部分发货 FBA 订单、FBA 库存的顺序读取，每批最多 200 条，按递增 ID 翻页。查询只选择计算需要的字段，不读取原始 JSON 或每行重复的连接资料；每页之间让出事件循环。
- 保持按产品合并跨店铺数据、按店铺隔离未匹配 SKU、负发货数量归零、仅将已匹配产品计入 FBA 合计等规则。
- 快照主表仅返回 ID，明细以每批 200 条批量插入。主表、全部明细和保留最近 30 份自动快照的清理仍在同一事务内；任一批失败会回滚。事务超时明确设置为 60 秒。
- 库存字段未变化时，不再为保存而重复序列化原始响应。变更及新增库存仍保留原始资料。
- Amazon 返回 429 且没有 Retry-After 时，重试基础等待从 250/500 毫秒调整为 1/2 秒，继续附带随机抖动、最多三次请求；有 Retry-After 时仍优先遵从原处理逻辑。
- OAuth 授权码及刷新令牌交换补上与其他请求相同的超时控制，默认 30 秒，避免网络无响应长期阻塞队列。

## 运行记录

新增结构化日志以 `Amazon sync` 开头，包含阶段、耗时、输入/输出条数、RSS 和已用 JS 堆内存（MiB）。阶段包括：

```text
all-start / all-complete / all-failed
store-start / store-complete / store-failed
snapshot-start / snapshot-skus / snapshot-orders / snapshot-inventory
snapshot-written / snapshot-complete / snapshot-skipped / snapshot-failed
```

这些是阶段采样，不是连续内存峰值监控。快照仍需要保存 SKU 映射与产品汇总 Map，内存占用会随唯一 SKU/产品数增长；没有声称总内存被限制为 200 条，也未在生产验证具体节省比例。

本次针对中午调查发现的资源风险实施优化，不能据此认定已经证实或完全消除当天故障的根因。

## 同步时间及 90 天窗口

2026-10-15 13:17 左右（日本时间）另行完成线上时间配置调整：每日中国时间 16:00、日本时间 17:00，时区仍为 `Asia/Shanghai`。生产 `.env` 的 `AMAZON_SP_API_SYNC_CRON` 已设为 `0 0 16 * * *`，沿用原运行镜像重新创建 API 容器，并确认运行环境只有此一项变化、站点可响应。原配置备份在服务器 `/root/.wms-config-backups/env-before-amazon-time-20261015-121729`。

本地服务默认值、Compose 默认值、三份环境变量示例和 API 说明已同步调整，避免后续部署恢复旧时间。时间配置先于本次代码发布单独在线上生效。

90 天是补货建议、销量统计和无销量判定的统计窗口，不表示每天从 Amazon 重新拉取完整的 90 天订单。FBA 首次同步默认回溯 90 天；已有水位后，按上次成功的订单同步起始时间前移 6 小时查询更新。FBM 首次同步只建立今后同步的边界，不补拉历史订单，后续也按自己的水位增量查询。销售快照则读取本地近 90 天数据。此次保留该统计口径。

# 乐天订单处理流程

同一 RMS 连接、同一订单展示一条处理流程，单号回传和每封邮件保留独立记录。保留原有唯一键及结果记录；仅清理废弃的新規确认标记，不重建历史任务。流程状态由当前订单事实、店铺开关及已有任务计算，不另存一套可能与实际结果冲突的完成标记。

## 范围与执行周期

- 首次导入时间：同一连接、同一订单所有 WMS 明细的最早 `createdAt`，不早于日本时间 2026-10-01 00:00（UTC 2026-09-30 15:00）。新增明细不会让旧订单重新进入范围。
- 默认定时周期：全天每 20 分钟。
- 默认部署配置保持暂停。环境开关仅初始化数据库中的定时设置；之后以自动处理中心分别保存的订单导入、单号回传、邮件发送开关为准，重启不重置。环境已有自定义 CRON 时需同步检查配置。
- 本次实现不部署、不改运行中环境，不联系乐天接口或 SMTP。
- 同一个定时入口每 20 分钟先执行已启用的 API 导入，再执行已启用的物流查询，等待结果写入 WMS 后检查单号与邮件；不再另设每日 05:00 的物流任务。物流查询由独立开关控制，开启时不受回传/邮件暂停影响。
- 只查询中国侧未签收、状态异常、未识别清关或缺少清关日期的单号；单号去重，已签收且清关信息完整的包裹停止常规查询。单轮默认最多 500 个单号，按最久未检查优先轮转，大量积压时不保证所有单号每轮都能查询。
- 物流同步失败或与其他实例/人工任务发生锁冲突时，仍按已保存的物流信息检查订单；日本侧正常流程继续，中国侧只有已有数据满足清关条件才会执行。定时入口禁止本实例重叠执行，物流与订单执行继续使用各自数据库锁。

## 流程

| 类型 | 邮件顺序 | 单号步骤 |
| --- | --- | --- |
| 日本发 | 新規 → 日本発 | 仓库确认全部日本侧包裹实际出货、单号及登记日期齐全后回传 |
| 中国发 | 新規 → 中国発1 → 中国発2 | 中国侧全部目标明细单号、通関許可及清关日期齐全后回传 |
| 日中混发（未人工拆包） | 新規 → 混発1 → 混発2 | 仅回传中国侧，条件同中国发 |

邮件等待不阻塞单号回传。中国発1在中国侧单号及登记日期齐全后触发；混発1在日本侧单号及登记日期齐全后触发。第二封需第一封完成、全部中国侧清关且回传已完成。

中国発1、混発1按条件生成；尚未取得单号或尚未确认日本侧实际出货时，没有第一封任务属于正常等待，第二封不因此转为人工异常。条件齐全但尚未整理出第一封任务时，等待下一轮生成及完成。缺少新規任务、已有邮件失败到上限或发送结果不确定、回传后包裹信息变化等异常仍需人工核对；人工取消第一封则停止第二封，人工忽略第一封则允许按其他条件继续。

## 展示状态

- 等待条件：包裹未齐、尚未清关、前置步骤未完成、功能停用或正在执行。业务等待不消耗重试次数。
- 可以执行：条件满足，等待定时或人工执行。
- 等待人工：特殊说明、组合信息缺失、缺少新規等应已存在的任务、订单取消申请或未解决变更、发送结果不确定、完成后单号信息变化、店铺暂停、缺少启用模板。
- 执行异常：接口失败及重试等待。按原有退避和最大 10 次规则处理。
- 已结束：分别保留已发送、已回传、已核实外部单号、已忽略或已取消等实际结果。

明确取消的订单（明细状态900，或已跳过回传记录明确保存乐天状态900）按“订单已取消，流程已终止”展示，退出“需要人工”和“处理中”。API仅导入300订单，因此取消事实可以来自后续回传时的查询结果。已发送邮件和已完成回传保留原结果与时间；未完成或尚未生成的步骤不再提供执行、重试或忽略操作。仅计算流程状态，不删除订单或覆盖历史任务。状态800取消申请、其他非待发货状态、人工忽略回传及未核实的跳过不视作已取消。

已完成回传后出现“信息变化待核对”，且用户已在乐天手动回传全部包裹时，使用“已人工回传，忽略提醒”。系统只读取乐天原订单，逐个核对送付先、单号、配送公司及発送日，全部一致后更新当前包裹校验记录并保存人工核实日志；保留原回传结果、完成时间及接口响应，不执行回传或发送邮件。核实期间包裹发生变化、乐天资料不一致、订单取消或资料不完整时保留提醒。后续待发送邮件仍按原有条件处理，已发送邮件不重发。普通待回传或失败任务仍使用“忽略回传”，此操作不等于核实乐天已收到单号。

## 邮件内容与人工处理

当前地址、商品名称与数量、分仓明细、快递信息自动生成。组合的购买汇总保留原组合名称；分仓列表展示组件商品及数量。

人工修改过订单且存在订单备注时，将备注视作需要人工核对的特殊说明；数量或非组合 SKU 与原乐天购买信息不一致时也需核对，避免原金额与修改后商品不一致；不把内部备注直接自动发给买家。组合缺少原组合名称、组合 SKU、组件标识、商品名、有效数量或送付先信息时需人工确认。内容确认规则适用于五种商品/发货邮件；新規固定受理通知不参与商品内容确认。仅修改结构化信息且没有特殊说明、或组合信息完整，不因“修改过/组合订单”标签强制人工确认。

确认使用即时预览、模板版本、订单指纹与修改后的正文；指纹涵盖清关日期和人工确认相关字段。发送前订单变化则必须重新预览。定时和人工均要求已启用的实际模板版本；默认内容只用于编辑预览，人工恢复默认时保存并启用一个真实版本。

乐天已有日本侧单号时：单号记为已核实，无法确认由本系统请求回传时，创建结果待确认的日本発任务，不自动补发。人工确认已发送，或确认重发后继续。发送回传请求前持久记录请求意图；重试时结合乐天侧单号核实，不能仅凭尝试次数认定系统已回传。Message-ID 不作为外部投递去重保证。

缺少历史新規或日本発任务不自动猜测补发。订单进度页可在核实发送记录后选择“生成邮件任务”或“确认无需发送”。前者恢复正常发送流程，后者记录人工忽略并允许后续邮件。

已完成后单号、配送公司、日期或发货范围变化，进度页转人工；人工恢复回传任务后再次核对乐天。已发送邮件不会因此自动重发。

“忽略”满足后续邮件前置条件；“取消”阻断后续邮件。重试只恢复该任务，不清除店铺异常暂停。店铺异常暂停需通过明确的“恢复”操作人工解除。

## 队列与界面

候选订单和执行任务按游标轮转；未就绪的前 500 个订单、待人工的前 100 封邮件不能长期挡住后续任务。游标是进程内扫描进度，重启后从头检查，数据库唯一键及任务认领防止重复生成和并发执行。

乐天订单主页面提供“从乐天 API 导入”“自动处理中心”“批量操作”三组入口；仅批量删除/改号按需展开。店铺管理也使用同一个处理中心入口。

处理中心默认打开“需要人工”，只展示需要处理的步骤；“处理中”展示完整订单流程；“处理记录”集中查看邮件、单号及运行记录；“店铺设置”集中配置连接、模板和查看店铺异常。人工页默认只展示待处理步骤，可展开查看该订单的完整流程。普通可执行步骤支持勾选批量处理；需要确认正文的邮件逐封处理。忽略回传、确认外部已发送以及重试均保留在对应步骤。人工/处理中视图先按所有符合范围的订单计算状态，再分页，避免只筛当前页而遗漏任务。批量读取事实，每批最多100个订单。

立即检查、任务整理归入“更多工具”。CSV备用回传及当日邮件用CSV已整体删除。查看进度不生成任务、不发送；“整理待处理任务”只整理本地任务。原有记录保留。

## API 导入与新規邮件

API 导入不再注册独立的15分钟调度，统一使用 `RAKUTEN_RMS_AUTOMATION_CRON`（默认每20分钟、日本时间）。每轮依次执行 API 导入及本次新規邮件、物流同步、单号及后续邮件处理。定时导入仍受 `RAKUTEN_RMS_API_SCHEDULED_SYNC_ENABLED` 和 `RAKUTEN_RMS_API_SCHEDULED_SYNC_PAUSED` 控制；回传及邮件仍受独立发送暂停开关控制，默认不启用真实发送。旧导入 cron/时区配置不再生效。

“立即检查（全部店铺）”主动导入已开启订单同步的店铺，再执行相同流程，仍遵守发送暂停；只是查看/刷新页面不触发该操作。统一流程禁止本实例定时与人工重叠；某店铺导入失败不阻止其他店铺和现有订单处理。

API 仅导入状态300订单，按删除范围排除整单或已删商品明细。首次查询回查7天，后续保留6小时重叠窗口。首次导入日期仅决定自动处理资格，不等同于乐天订单日期。所有新建 API 订单保存唯一新規任务，在提交后立即按发送设置处理；首次同步、间隔超过40分钟、商品修改、组合订单和通知关闭都不再强制内容确认。通知关闭时任务等待；重新开启后按正常条件处理。认领已有CSV、更新已有订单不新建新規任务；重复导入不覆盖既有任务。

所有真实邮件发送前再次查询乐天订单状态。取消申请/取消状态800、900及无法识别状态停止发送并转人工；新規只有状态300允许发送，已离开待发货的订单需核对并忽略过时邮件。查不到目标订单、返回其他订单或无法识别的核实异常均停止并转人工。明确的临时网络故障允许20分钟后重新查询；这些检查均不发送邮件、不消耗SMTP发送尝试次数。人工确认不绕过最新状态检查。

## 人工取消与逻辑删除

同一订单号按产品明细导入。用户勾选明细后点击唯一的“批量删除”按钮，只提交所选明细ID，后台在事务中读取这些订单的全部未删除明细，逐单判断范围，包含其他分页及筛选外的产品：

- **只勾选部分产品**：仅标记勾选明细的 `deletedAt`、`deletedBy`，保留其他产品。API明细按RMS商品明细键永久排除；无该键的CSV商品按店铺、订单号及SKU记录排除。
- **勾选该订单全部未删除产品**：按整单删除处理，建立整单永久导入排除，终止未完成单号与邮件任务。此前已删除明细不计入当前需要勾选的产品数量。

一次选择多个订单时，每个订单独立判断，可同时发生整单删除和部分产品删除。返回删除明细数、整单删除订单数、部分产品删除订单数。API连接使用连接ID和订单号识别整单，不依赖可变店名；CSV按店铺和订单号隔离。

部分商品删除时，剩余产品继续参与拣货、物流及单号回传；后续商品邮件按剩余明细生成，并要求人工确认正文，不沿用原整单金额或已删商品信息。API同步保留商品删除确认标记。自动处理资格按整单最早导入时间计算（包括已删明细），删除最早的一条商品不能使旧订单重新进入自动发送范围。固定新規受理通知仍不参与商品内容确认。已发送邮件和已完成回传不重置；包裹范围或发货类型变化时按现有规则转人工核对。单笔邮件恢复判断是否仍有可处理明细，不因订单内存在一条已删产品而封锁其他产品。

已删除明细保留历史资料，普通订单列表、搜索、出库/物流、CSV导出、自动流程候选均排除。API、CSV重导及同步回滚不能恢复已删商品；整单删除则永久禁止重新导入整单。已经完成或发送结果不确定的记录保留为证据。

两类删除均与外部发送共用店铺执行锁；店铺正在回传/发送时拒绝删除。API写入事务锁定店铺行，与删除事务串行。只核对本次将删除明细的拣货关联，已关联拣货的产品需先由仓库处理；删除一个未关联产品不应因另一产品已进入拣货而被阻断。系统不会根据买家/API状态自动删除，也不会自动向乐天或仓库发送取消请求。

上线前需执行迁移 `20261013120000_rakuten_order_soft_delete`；本次仅准备代码、迁移与测试，不执行线上迁移或部署。此前已物理删除的资料不会被此次迁移恢复。

## 导入后直接发送新規

所有 API 正式导入入口共用导入后回调。订单及邮件任务在同一事务内保存；事务提交成功后，只处理本次新增订单的新規任务。导入失败/回滚不发送；重复同步不会重新发送已完成任务。不执行物流查询、单号回传或其他邮件。批量导入按100个订单分批检查，避免前100封遮挡其余订单。

直接发送复用邮件执行器和店铺锁，继续检查启用模板、收件人、最新乐天状态、逻辑删除、失败退避及发送结果不确定；新規不检查商品内容确认。暂停、店铺异常或店铺正忙时保留任务，不绕过开关。SMTP或运行记录失败只反馈邮件延期，不将已提交的导入标记为失败。每20分钟的统一任务继续补查遗漏、重试到期邮件和后续阶段。

## 日本发仓库出货节点与旧逻辑清理

日本发具体流程见 [日本发订单完整流程](rakuten-japan-order-flow.md)。以仓库点击“5.确认本批次作业完成及出货”为出货确认：全部面单已打印、无待完成打印/补打、批次处于可完成状态，且订单单号和数量匹配后，记录批次完成时间/操作人及日本侧订单出货确认。上传PDF或打印本身不算出货。旧批次完成但没有新出货确认时间时，允许人工再次确认，不用旧更新时间猜测出货时间。

日本发回传及日本発邮件都等待全部日本明细出货确认；発送日用日本时间的仓库确认日。回传成功时即使邮件通知关闭也保存日本発任务，开关只控制发送。单号回传统一走处理中心API，不再提供CSV备用路径。中国侧日期统一使用清关日期。

删除隐藏的旧人工清单及其状态、筛选和事件处理；删除旧全店同步、独立店铺自动执行接口和另一套手工清单状态计算。中心用统一订单流程显示状态，任务整理仅准备任务、不执行外部动作，并使用店铺锁。保留唯一键、已发送快照、SMTP不确定状态、外部单号核实及显式人工恢复，它们是防重复与历史证据。

新增部署迁移：`20261013130000_rakuten_fixed_new_order_ack` 清理未开始发送的新規旧确认标记；`20261013140000_rakuten_warehouse_dispatch_confirmation` 增加真实出货确认时间/操作人。既有软删除迁移仍需部署。迁移不重置已发送、结果不确定或人为取消邮件，也不推测旧批次出货时间。本次未部署、未执行迁移或真实订单操作。

独立手动快递同步入口、前端调用和POST接口已删除。快递状态由统一流程每20分钟检查；只读状态汇总保留。最近15天、最近30天及全部的乐天回传CSV下载已整体删除。

## 执行安全规则（2026年10月13日确认）

混发只回传中国侧；已有回传按送付先及单号核实，不新增物流公司/日期匹配要求。所有回传必须等待新規已发送或明确人工忽略。失锁或心跳失败停止后续外部操作；已在途操作无法撤回。SMTP必须明确接受买家地址，只有BCC成功不能记客户邮件成功。领取邮件任务后重新核对逻辑删除、业务变更、发货类型、出货/清关、回传及前置邮件条件，并核对人工预览事实。运行记录超过30分钟但执行锁心跳仍有效不判中断；失联后才恢复超时任务，已开始SMTP的任务转结果不确定。

## 2026年10月14日执行判断、模板和积压优化

回传的业务条件集中在同一判断函数，处理中心展示、人工执行、定时执行及领取后的复查共用。邮件的删除/业务变更、发货范围、仓库出货/清关及回传条件共用同一判断；前置邮件与人工正文确认仍独立检查。店铺锁、外部实时核实和SMTP买家地址接受检查作为外部动作保护保留。

单笔读取、模板查询、任务准备及发送前检查错误被隔离，不阻止同店后续订单；错误写运行日志，执行阶段计失败。店铺认证异常仍暂停环节，失锁仍停止整店本轮。数据库持续不可用不能保证写入该笔异常记录，后续定时仍按持久状态恢复，不猜发送结果。

健康检查读取当前已启用模板，标出旧“本日発送”及中国侧“设置最短送达日”文案。保存、启用和发送均拦截这类旧模板；页面不将无效模板显示为可执行。管理员在模板管理修订，保存新版后明确启用，旧版本与已发送正文保留，不自动覆盖或激活。本次未连接生产数据库修改存量模板。

积压显示最久等待时间、最近连续无完成轮次、最近成功时间。最久等待包含待处理、失败、结果不确定及需人工处理任务。连续无完成轮次按店铺最近已结束运行记录计算，遇回传或邮件完成即止，最多检查100轮并提示统计上限；这是店铺级无进展指标，不是每笔订单的尝试次数。有积压且连续3轮无完成产生告警，未积压不告警。不会仅凭运行记录为成功就认定订单已推进。

## 手工拆包与原乐天订单（2026年10月14日）

人工仍按原订单号后加A、B、C等方式设置内部包裹号。批量改号在事务内锁定目标号码并重新检查冲突，使用RepeatableRead保护尚不存在的号码范围；CSV订单及不同店铺的并发批量改号也执行相同校验。号码已被使用或事务发生锁冲突时回滚本次修改并提示刷新重试，不自动换号，不允许部分产品先保存。复用现有索引，无需新增迁移。

客户一个乐天订单购买多个产品、超过单包尺寸时，工作人员通过“批量修改订单号”，将所选产品的内部仓库订单号从 `12345678` 改为 `12345678A`，还可继续拆为B、C。原单号存入独立的 `rmsOrderId`；不根据A/B后缀猜关系，也不修改乐天侧的实际订单号。商品明细键、原始RMS送付先ID及购买资料保留，后续API同步不将内部包裹号改回原号。

仓库拣货、制单、打印、单号回写按内部订单号进行。处理中心、回传及邮件按同一RMS连接和原乐天订单号汇总，一条流程显示所有内部包裹号。拆分前后共用原新規及后续邮件唯一键，不因A/B内部号重复创建受理通知或发货邮件。

人工拆包订单需要汇总全部拆分包裹回传：日本侧须确认实际出货，单号与登记日期齐全；中国侧须满足通関許可及清关日期。全部包裹就绪后，对原乐天订单号调用一次updateOrderShipping，按原送付先ID填写每个不同快递单号。拆包混发同样汇总两侧包裹；未人工拆包的日中混发继续维持只回传中国侧的现有规则。已完成回传后包裹范围变化时，保留历史结果并由人工恢复核对，不自动重复发送旧邮件。

批量删除仍由后台判断，但以原乐天订单为范围，包含所有拆分包裹：仅勾选A包的产品时，原单其他产品继续处理；勾选原单及所有拆包的全部未删除产品时，才永久删除整单。商品级排除记录也关联原单号，阻止被删除的拆包商品通过API重新导入。

已有单号或关联拣货的产品继续禁止直接改号；拆分操作与店铺外部执行共用锁，并在事务中重新检查所选明细，避免回传期间改变包裹范围。

## 独立定时控制与运行状态（2026年10月14日）

自动处理中心上方展示四个全局定时开关：订单导入、物流自动查询、快递单号回传、邮件发送。每项独立保存在 `rakuten_schedule_controls`，不因切换店铺筛选或服务重启而改变。店铺自身的 `syncOrders`、`autoShippingEnabled`、`mailNotificationsEnabled` 及异常暂停仍然生效，全局开关不替代店铺开关。

统一定时入口默认在日本时间每小时 00、20、40 分执行，依次执行开启的导入、开启的物流查询、开启的回传、开启的邮件阶段。关闭邮件也停止导入后自动发送新規；订单和邮件任务仍保存，重新开启后按已有业务条件处理。四个开关均关闭时，不再自动启动这些阶段。物流开关默认开启以保持原有行为，页面关闭后独立保存；回传和邮件会继续按已保存的物流事实及原有业务条件判断，不会因为停止查询而假设已清关。关闭开关不会中断正在执行的一轮。

页面每5秒刷新。状态来自数据库执行锁和心跳，显示运行中、等待下一轮、暂停、执行中断或调度未启动，并保留最近一次开始时间、完成时间、结果及异常原因。数据库锁防止同一阶段跨实例重复启动，30分钟未收到心跳视为中断，可由下一轮认领恢复；已有订单任务和店铺锁继续负责业务去重。

下一次计划时间读取实际注册的定时器，支持既有自定义 CRON；关闭时不显示下一次时间。它是定时触发时间，前序处理尚未结束或上一轮仍在执行时，实际启动会延后或本次跳过。页面“立即检查”遵循四个自动开关，明确的人工导入和逐项执行仍走各自人工入口。

启用功能前需执行 `20261014100000_rakuten_schedule_controls` 数据库迁移。本地仅生成迁移文件，未迁移数据库或部署。

物流自动查询复用同一控制表，不需要额外数据库迁移。关闭开关停止后续定时查询，“立即检查”也遵循该开关。物流查询默认开启，首次展示或执行时初始化；关闭后服务重启不会恢复开启。

## 缺失组合配置的导入处理

定时导入和API手动导入遇到 `zh-` 组合ID未配置、组合没有明细或明细产品ID无效时，跳过该原乐天订单的全部商品，继续导入其他正常订单。不创建占位商品、出货任务或该订单的新規邮件；同单中普通商品也不单独进入仓库流程。

手动预览列出跳过订单及缺失组合ID，仍可确认导入其他正常订单。确认后和定时导入均在同一事务保存 `rakuten_order_import_issues`，按连接ID及原订单号去重。同步批次显示部分完成，并保留跳过数量、原因及待人工信息。自动处理中心上方显示待处理清单，可按店铺和订单号筛选、翻页，并前往组合产品配置。

补齐配置后，可重新预览并手动确认导入，或等待开启的定时导入。待处理订单号会额外通过getOrder重新查询，即使已超出正常增量查询窗口也不会遗失；成功处理后清除待处理状态。匹配冲突时保留记录并更新处理原因；订单已离开已识别的待发货状态或已被整单永久删除时关闭记录。RMS未返回订单或状态无法识别时保留待处理记录，不猜测已完成。回滚修复后的导入会重新打开对应待处理记录。

## 普通产品及组合组件的存在性检查

商品配置检查同时覆盖普通商品的产品ID及组合展开后的组件产品ID。任一需要导入的商品在主产品表中不存在（或未提供产品ID），整张原订单跳过，其他订单继续；主产品存在但库存为零仍按原缺货分仓规则导入，不作为资料缺失。

### 最后重点检查：邮件去重与异常人工处理

- 同店铺、原乐天订单号、邮件事件使用数据库唯一键；拆包和再次导入沿用同一任务。已发送任务不自动重置，发送领取使用条件更新，只有领取成功的执行者可以发送。
- SMTP发送开始后，无论超时、未知异常、拒绝、接受结果缺失、只有BCC接受或发送成功后的数据库写入失败，都进入“发送结果待确认”，不自动重试。进程中断后也保留发送开始标记，恢复时转人工。

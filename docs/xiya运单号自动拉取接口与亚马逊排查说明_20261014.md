# WMS 自动拉取 Xiya 运单号：接口说明与亚马逊排查

整理日期：2026-10-14  
依据：WMS 当前代码版本 `6ee1fb4`，以及《XYJG 对外接口统一文档》（2026-06-25）。

用途：供 Xiya 技术人员核对“亚马逊订单在 WMS 未取得快递号”的问题。本文描述当前 WMS 实际调用方式。真实密钥不包含在本文中。

**同日生产调查补充：已确认 `DGAZ Store亚马逊日本` 与 `DGAZ Tiktok日本` 不在 WMS 当前运单同步名单中，导致有快递号的记录未被查询、返回后也会被过滤。详见[生产调查报告](亚马逊与TikTok运单号未同步调查_20261014.md)。以下请求参数仍描述修复前实现。**

后续代码已实现每次同步从店铺设置生成名单，新增和改名无需再修改固定名单，详见[动态店铺名单说明](xiya运单动态店铺名单说明_20261014.md)。该行为需在修改部署后生效。

## 1. 调用方向与执行时间

**WMS 主动调用 Xiya 的物流单导出接口，读取订单号和运单号，再写回 WMS。**

- 自动执行：每天中国时间 17:00，即日本时间 18:00。
- 每次查询：`days=5`。
- 查询店铺：乐天 1 个、亚马逊 2 个，同一次请求查询。
- WMS 页面“同步 Xiya 运单号”按钮也调用同一同步逻辑。

`GET /api/orders/export` 与 `POST /api/orders/export/ack` 是 Xiya 从 WMS 拉订单及确认接收的另一组接口；接收回执本身不会给 WMS 登记快递号。

## 2. WMS 当前调用的 Xiya API

```http
GET http://103.236.55.93/api/external/logistics/rakuten
x-api-key: YOUR_XIYA_EXPORT_API_KEY
Accept: application/json
```

虽然路径包含 `rakuten`，当前 WMS 同时通过此接口查询乐天和亚马逊物流数据。

### 请求参数

| 参数 | 当前代码发送值 | 说明 |
| --- | --- | --- |
| `company_name` | 默认 `XYJG` | 可由 WMS 配置 `XIYA_COMPANY_NAME` 覆盖；需双方核对实际公司归属 |
| `storeName` | `DGAZ乐天日本,DGAZ亚马逊日本站,ArcDiary亚马逊日本站` | 英文逗号分隔，参数名大小写须一致 |
| `days` | `5` | 查询最近 5 天；需 Xiya 确认时间筛选具体依据 |

地址可由 WMS 配置 `XIYA_LOGISTICS_EXPORT_URL` 覆盖。上述地址和 `XYJG` 是当前代码及配置模板的默认值，本文没有核验生产环境覆盖值。

请求头密钥来自 WMS 配置 `XIYA_EXPORT_API_KEY`，由 Xiya 方提供；与 Xiya 调用 WMS 时使用的 `THIRD_PARTY_API_KEY` 用途不同。

### 完整请求示例

以下命令会对中文参数进行 URL 编码，密钥占位符需在本地替换：

```bash
curl --get 'http://103.236.55.93/api/external/logistics/rakuten' \
  --data-urlencode 'company_name=XYJG' \
  --data-urlencode 'storeName=DGAZ乐天日本,DGAZ亚马逊日本站,ArcDiary亚马逊日本站' \
  --data-urlencode 'days=5' \
  --header 'x-api-key: YOUR_XIYA_EXPORT_API_KEY' \
  --header 'Accept: application/json'
```

## 3. 返回结构与字段要求

WMS 要求 HTTP 状态成功、业务 `code` 为 `0` 或 `200`，且 `data.rows` 为数组。WMS 只读取本次返回的 `data.rows`，没有自动翻页逻辑。

以下为结构示例，订单号、运单号均为虚构值：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "total": 2,
    "rows": [
      {
        "id": 1001,
        "sales_order_id": "249-1234567-1234567",
        "store_name": "DGAZ亚马逊日本站",
        "logistics_order_id": "123456789012",
        "tracking_number": "123456789012",
        "shipping_method": "SAGAWA-01",
        "created_at": "2026-10-14T08:15:30+08:00",
        "logistics_status": "已发货"
      },
      {
        "id": 1002,
        "sales_order_id": "250-1234567-1234567",
        "store_name": "ArcDiary亚马逊日本站",
        "logistics_order_id": "234567890123",
        "tracking_number": "234567890123",
        "shipping_method": "YAMATO-01",
        "created_at": "2026-10-14T09:15:30+08:00",
        "logistics_status": "已发货"
      }
    ]
  }
}
```

上例为两个单号字段相同的情形，不代表双方已确认两个字段含义相同；含义差异见第 4 节。

| 字段 | WMS 当前处理方式 |
| --- | --- |
| `store_name` | 必须为当前支持的 3 个店铺名之一；去掉首尾空白后精确匹配，其他名称整条跳过 |
| `sales_order_id` | 必须非空；用于匹配 WMS 平台订单号 `orderId`，例如完整亚马逊订单号 `249-1234567-1234567` |
| `logistics_order_id` | 当前优先作为 WMS 运单号写入 |
| `tracking_number` | 仅当 `logistics_order_id` 为假值（如空字符串、null、缺失）时作为备用运单号 |
| `created_at` | 用于运单登记时间及重复记录排序；建议返回带时区的 ISO 8601 时间。缺失或无效时，WMS 使用同步时刻 |
| `shipping_method` | `SAGAWA-01` 对应 `Xiya-SAGAWA`；`YAMATO-01` 对应 `Xiya-YAMATO`；其他值对应 `Xiya` |
| `id` | 物流记录内部 ID，当前不用于匹配 WMS 订单 |
| `logistics_status` | 当前不参与是否写入运单号的筛选 |
| `total` | 当前不参与写入或分页，仅处理 `rows` 实际内容 |

运输方式字段的读取顺序为：`运输方式名称` → `shipping_method` → `shipping_method_name` → `delivery_method_name` → `logistics_method_name` → `transport_method_name`。代码使用第一个非 null / undefined 字段；空字符串也会占据该位置。

运单号应返回字符串，避免丢失前导零。若 `logistics_order_id` 仅为空格，当前代码会先选中它，再去掉空白，最终因单号为空而跳过，不会继续读取 `tracking_number`。

## 4. 请双方优先确认的字段差异

现有 Xiya 文档定义：

- `logistics_order_id`：系统内部物流订单编号。
- `tracking_number`：快递运单号（跟踪号）。

**WMS 当前实现却优先将 `logistics_order_id` 写入快递号，仅在其为空时读取 `tracking_number`。** 如果这两个字段不同，WMS 可能写入内部物流编号，而非真实快递号。该差异需要双方确认；本次仅整理接口，没有修改代码。

另据现有 Xiya 文档，导出接口仅返回 `logistics_order_id` 不为空的记录。请确认：亚马逊物流单是否也会填充该字段？是否存在已经有 `tracking_number`，但因 `logistics_order_id` 为空而未被导出的记录？

## 5. 亚马逊回传后，WMS 的匹配条件

| 检查项 | 当前规则 |
| --- | --- |
| 支持的亚马逊店铺名 | 精确为 `DGAZ亚马逊日本站` 或 `ArcDiary亚马逊日本站` |
| 订单关联 | 用 `sales_order_id` 匹配 WMS `orderId`；去掉返回值首尾空白，不会自动移除前缀、后缀或转换其他订单编号 |
| WMS 现有运单 | 只更新运单号为 null 或空字符串的明细，不覆盖已有运单 |
| 亚马逊记录来源 | 排除 `sourceKind=sp_api` 的看板数据；订单处理记录才进入此同步范围 |
| 中国发资格 | 发货方式明确为 `china_pending` / `china_no_stock`；或 `fulfillmentMode=xiya_api` 且不在有效的海外仓拣货批次中 |
| 同订单多条物流记录 | 按平台来源与订单号去重，保留 `created_at` 最新的一条；时间相同时保留响应中后出现的一条 |
| 同订单多商品明细 | 同一订单号下符合条件的明细写入同一个运单号，当前不按商品明细匹配多个包裹 |

当前亚马逊匹配用订单号查询，不再按 WMS 订单的店铺名二次筛选；返回的店铺名用于判断平台来源。去重也不包含店铺名。

手动订单另外按订单号匹配同批返回数据。因此，若某笔“亚马逊订单”实际建立在 WMS 手动订单模块，其更新计数可能出现在 `manualUpdatedCount`。

## 6. 请 Xiya 协助核对并提供的资料

请选取一笔“Xiya 已有快递号、WMS 尚无快递号”的亚马逊订单，完成以下核对：

1. 确认该订单在 Xiya 所属公司是否为 `XYJG`，以及接口密钥是否有该公司的导出权限。现有文档示例使用 `DGAZ`，WMS 默认使用 `XYJG`，需确认双方实际配置。
2. 用第 2 节完全相同的参数查询，确认 `data.rows` 是否包含该订单。
3. 分别单独查询 `DGAZ亚马逊日本站` 和 `ArcDiary亚马逊日本站`，比较与逗号分隔多店铺查询的结果；确认 `/rakuten` 接口确实支持两个亚马逊店铺。
4. 检查实际返回的 `store_name`、`sales_order_id`、`logistics_order_id`、`tracking_number`，尤其确认销售订单号仍为原始亚马逊订单号。
5. 确认 `days=5` 按物流单创建时间、更新时间还是快递号生成时间筛选。如果旧物流单后来才取得快递号，是否会因创建时间超出 5 天而漏掉？如需扩大天数排查，请确认接口允许的范围。
6. 确认接口是否有默认分页、条数上限或只导出特定物流状态；如有，请提供完整规则，因为当前 WMS 没有翻页逻辑。
7. 明确两个单号字段的含义，并提供一条两个字段不同的样例（若存在），供双方确定 WMS 应写入哪个字段。

请回传：故障亚马逊订单号、Xiya 实际公司和店铺名、查询时间及参数、HTTP 状态、完整业务响应（至少包含故障订单行），以及时间筛选和单号字段的定义。提供响应时无需包含密钥或买家信息。

单店铺诊断示例（当前自动任务仍使用 3 店铺合并请求）：

```bash
curl --get 'http://103.236.55.93/api/external/logistics/rakuten' \
  --data-urlencode 'company_name=XYJG' \
  --data-urlencode 'storeName=DGAZ亚马逊日本站' \
  --data-urlencode 'days=5' \
  --header 'x-api-key: YOUR_XIYA_EXPORT_API_KEY' \
  --header 'Accept: application/json'
```

查询另一店铺时，将 `storeName` 改为 `ArcDiary亚马逊日本站`。若第 1 项确认公司配置不同，按双方确认值查询并同步核对 WMS 配置。

## 7. WMS 侧同步结果核对

WMS 内部手动触发入口：`POST /api/orders/china-orders/sync-xiya-tracking`，使用 WMS 登录 JWT（`Authorization: Bearer ...`），无请求体。此入口由 WMS 操作人员调用；Xiya 对接的物流导出 API 见第 2 节。

| 同步结果字段 | 含义 |
| --- | --- |
| `syncedAt` | 本次同步结束时间，UTC ISO 字符串 |
| `days` | 查询天数，当前为 5 |
| `fetchedCount` | Xiya 返回的原始物流行数 |
| `validCount` | 店铺名可识别、订单号和所选运单号均非空的有效行数 |
| `deduplicatedCount` | 按平台来源及订单号去重后的候选行数 |
| `rakutenUpdatedCount` | 实际更新的乐天订单明细数 |
| `amazonUpdatedCount` | 实际更新的亚马逊订单明细数 |
| `manualUpdatedCount` | 实际更新的手动订单明细数 |
| `skippedUnmatchedCount` | 乐天、亚马逊、手动三次匹配的未匹配候选数之和；不是唯一未匹配订单数，同一候选可能重复计入 |

判断顺序：先看故障订单是否进入原始 `rows`，再看字段是否符合要求，最后由 WMS 核对订单号及中国发资格。`amazonUpdatedCount=0` 本身不能证明 Xiya 没有返回亚马逊记录；已有运单或不符合 WMS 筛选条件也会导致不更新。
